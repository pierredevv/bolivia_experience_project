## ADR-220 (Revisado): Consultas Geoespaciales — Prisma + PostGIS

**Fecha:** 2026-06-26
**Estado:** Aceptado
**Revisado:** 2026-06-26 (añadido detalle de implementación)

---

### Contexto

BoliviaExperience requiere funcionalidad de geolocalización para:
- Buscar lugares cercanos a la ubicación del usuario ("Cerca de Ti")
- Filtrar por categoría en un área geográfica
- Mostrar marcadores en el mapa con clustering
- Calcular distancias entre el usuario y los lugares

La base de datos es PostgreSQL 15 con extensión PostGIS (ADR-204). El ORM seleccionado es Prisma 5.x (ADR-205).

**Problema:** Prisma tiene soporte limitado para PostGIS:
- No soporta tipos `geography` o `geometry` nativamente
- No permite usar funciones PostGIS (`ST_DWithin`, `ST_Distance`, etc.) en queries tipadas
- El campo `location GEOGRAPHY(POINT, 4326)` no se mapea automáticamente

---

### Opciones Consideradas

#### Opción A — Knex.js como query builder para geoespacial

- **Ventajas:**
  - Soporte nativo para raw SQL
  - Control total sobre queries geoespaciales
  - Bien documentado
- **Desventajas:**
  - Dos ORMs/query builders en el proyecto (Prisma + Knex)
  - Duplicación de configuración de conexión
  - Mayor complejidad en testing
  - Curva de aprendizaje adicional para el equipo

#### Opción B — TypeORM en lugar de Prisma

- **Ventajas:**
  - Soporte nativo para columnas PostGIS
  - Decoradores para tipos personalizados
  - Raw queries integradas
- **Desventajas:**
  - Migrar de Prisma a TypeORM requiere reescribir todo el acceso a datos
  - TypeORM tiene más boilerplate que Prisma
  - Menor DX (Developer Experience) que Prisma
  - Prisma ya seleccionado en ADR-205

#### Opción C — Prisma raw queries ($queryRaw, $executeRaw) ✅ SELECCIONADA

- **Ventajas:**
  - Reutilizar Prisma para 95% del CRUD (usuarios, categorías, reviews, favoritos, etc.)
  - Raw queries solo para el 5% geoespacial (nearby, cluster, bounds)
  - Un solo ORM en el proyecto
  - Conexión a DB centralizada en Prisma Client
  - Transacciones Prisma incluyen raw queries
- **Desventajas:**
  - Queries geoespaciales sin type safety de Prisma
  - Necesidad de mapear resultados manualmente
  - SQL raw expuesto en el código

#### Opción D — PostGIS + GraphQL spatial extensions

- **Ventajas:**
  - API GraphQL para consultas espaciales
- **Desventajas:**
  - No usamos GraphQL (ADR-224: RESTful)
  - Complejidad innecesaria

---

### Decisión

**Opción C: Prisma raw queries para geoespacial + Prisma ORM para CRUD**

**Nota sobre `location`:** El campo `location GEOGRAPHY(POINT, 4326)` es una columna generada (GENERATED ALWAYS AS) en PostgreSQL. Prisma no lo mapea, pero tampoco lo rompe. Se ignora en el schema y se maneja via raw queries.

#### 2. Repositorio Geoespacial (Raw Queries)

```typescript
// src/modules/places/repositories/geo.repository.ts

import { Injectable } from '@nestjs/common';
import { PrismaService } from '../../../prisma/prisma.service';

export interface NearbyPlace {
  id: string;
  name: string;
  description: string | null;
  address: string;
  phone: string | null;
  rating_avg: number;
  rating_count: number;
  category_name: string;
  category_icon: string;
  primary_photo: string | null;
  distance_meters: number;
}

export interface ClusterResult {
  cluster_id: number;
  cluster_count: number;
  avg_lat: number;
  avg_lng: number;
}

@Injectable()
export class GeoRepository {
  constructor(private readonly prisma: PrismaService) {}

  /**
   * Buscar lugares cercanos a una ubicación (radio en metros)
   */
  async findNearby(
    latitude: number,
    longitude: number,
    radiusMeters: number = 5000,
    limit: number = 20,
    categoryId?: string,
  ): Promise<NearbyPlace[]> {
    const categoryFilter = categoryId
      ? `AND p.category_id = $4`
      : '';

    const params = categoryId
      ? [latitude, longitude, radiusMeters, categoryId]
      : [latitude, longitude, radiusMeters];

    const query = `
      SELECT 
        p.id,
        p.name,
        p.description,
        p.address,
        p.phone,
        p.rating_avg,
        p.rating_count,
        c.name as category_name,
        c.icon as category_icon,
        (
          SELECT url FROM place_photos 
          WHERE place_id = p.id 
          ORDER BY display_order 
          LIMIT 1
        ) as primary_photo,
        ST_Distance(
          p.location::geography,
          ST_SetSRID(ST_MakePoint($2, $1), 4326)::geography
        ) as distance_meters
      FROM places p
      JOIN categories c ON p.category_id = c.id
      WHERE ST_DWithin(
        p.location::geography,
        ST_SetSRID(ST_MakePoint($2, $1), 4326)::geography,
        $3
      )
      AND p.is_active = true
      ${categoryFilter}
      ORDER BY distance_meters ASC
      LIMIT ${limit}
    `;

    return this.prisma.$queryRawUnsafe<NearbyPlace[]>(query, ...params);
  }

  /**
   * Clustering de marcadores para el mapa (zoom bajo)
   */
  async findClusters(
    northEastLat: number,
    northEastLng: number,
    southWestLat: number,
    southWestLng: number,
    epsMeters: number = 500,
  ): Promise<ClusterResult[]> {
    const query = `
      WITH clustered AS (
        SELECT 
          id,
          latitude,
          longitude,
          ST_ClusterDBSCAN(
            location, 
            eps := $5, 
            minpoints := 2
          ) OVER () as cluster_id
        FROM places
        WHERE is_active = true
        AND latitude BETWEEN $4 AND $1
        AND longitude BETWEEN $2 AND $3
      )
      SELECT 
        COALESCE(cluster_id, -1) as cluster_id,
        COUNT(*) as cluster_count,
        AVG(latitude)::DECIMAL(10,8) as avg_lat,
        AVG(longitude)::DECIMAL(11,8) as avg_lng
      FROM clustered
      GROUP BY cluster_id
      ORDER BY cluster_count DESC
    `;

    return this.prisma.$queryRawUnsafe<ClusterResult[]>(
      query,
      northEastLat,
      southWestLng,
      northEastLng,
      southWestLat,
      epsMeters,
    );
  }

  /**
   * Buscar lugares dentro de un bounding box (viewport del mapa)
   */
  async findByBounds(
    northEastLat: number,
    northEastLng: number,
    southWestLat: number,
    southWestLng: number,
    categoryId?: string,
  ): Promise<NearbyPlace[]> {
    const categoryFilter = categoryId
      ? `AND p.category_id = $5`
      : '';

    const params = categoryId
      ? [northEastLat, northEastLng, southWestLat, southWestLng, categoryId]
      : [northEastLat, northEastLng, southWestLat, southWestLng];

    const query = `
      SELECT 
        p.id,
        p.name,
        p.description,
        p.address,
        p.phone,
        p.rating_avg,
        p.rating_count,
        c.name as category_name,
        c.icon as category_icon,
        (
          SELECT url FROM place_photos 
          WHERE place_id = p.id 
          ORDER BY display_order 
          LIMIT 1
        ) as primary_photo,
        0 as distance_meters
      FROM places p
      JOIN categories c ON p.category_id = c.id
      WHERE p.is_active = true
      AND p.latitude BETWEEN $3 AND $1
      AND p.longitude BETWEEN $4 AND $2
      ${categoryFilter}
      ORDER BY p.rating_avg DESC, p.rating_count DESC
      LIMIT 100
    `;

    return this.prisma.$queryRawUnsafe<NearbyPlace[]>(query, ...params);
  }
}
```

### Consecuencias

**Positivas:**
- Un solo ORM (Prisma) para el 95% de las operaciones
- Raw queries encapsuladas en un repositorio dedicado
- Transacciones de Prisma incluyen operaciones geoespaciales
- Type safety para CRUD, flexibilidad para geoespacial
- Fácil de testear (mock del repositorio)

**Negativas:**
- Queries geoespaciales sin type safety de Prisma
- SQL raw expuesto en el código (mantener limpio)
- Duplicación de lógica de selección de columnas

**Deuda Técnica:**
- Cuando Prisma soporte PostGIS nativamente, migrar las raw queries a Prisma Client
- Monitorear: https://github.com/prisma/prisma/issues/7744

**Mitigaciones:**
- Repositorio dedicado (`GeoRepository`) con interfaz tipada
- Tests unitarios para cada query geoespacial
- Documentación inline de cada query
