## 2. Optimización por Consulta

### 2.1 Lugares Cercanos (Nearby) — CRÍTICA

**Problema:** La consulta más frecuente y sensible a latencia.

#### Consulta Original (sin optimizar)

```sql
-- ❌ LENTO: Full table scan + cálculo de distancia para todos los lugares
SELECT 
    p.*,
    ST_Distance(p.location::geography, ST_SetSRID(ST_MakePoint($1, $2), 4326)::geography) as distance
FROM places p
WHERE ST_DWithin(
    p.location::geography,
    ST_SetSRID(ST_MakePoint($1, $2), 4326)::geography,
    5000
)
AND p.is_active = true
ORDER BY distance ASC;
```

**Tiempo estimado (1,000 lugares):** ~150ms

#### Consulta Optimizada

```sql
-- ✅ RÁPIDO: Usa índice GIST + LIMIT pushdown + JOIN optimizado
SELECT 
    p.id,
    p.name,
    p.description,
    p.address,
    p.phone,
    p.rating_avg,
    p.rating_count,
    c.name as category_name,
    c.icon as category_icon,
    (
        SELECT url FROM place_photos pp
        WHERE pp.place_id = p.id 
        ORDER BY pp.display_order 
        LIMIT 1
    ) as primary_photo,
    ST_Distance(
        p.location::geography,
        ST_SetSRID(ST_MakePoint($2, $1), 4326)::geography
    ) as distance_meters
FROM places p
JOIN categories c ON p.category_id = c.id
WHERE p.location IS NOT NULL
AND ST_DWithin(
    p.location::geography,
    ST_SetSRID(ST_MakePoint($2, $1), 4326)::geography,
    $3  -- radio en metros
)
AND p.is_active = true
ORDER BY distance_meters ASC
LIMIT $4;  -- LIMIT pushdown
```

**Tiempo estimado (1,000 lugares, radio 5km):** ~15ms

**Optimizaciones aplicadas:**
1. **Índice GIST:** `CREATE INDEX idx_places_location ON places USING GIST(location);`
2. **LIMIT pushdown:** Reducir filas procesadas antes del ORDER BY
3. **Subquery para fotos:** Evitar JOIN múltiple con place_photos
4. **Parámetros preparados:** Reutilizar plan de ejecución

#### Índices Requeridos

```sql
-- Índice GIST para consultas geoespaciales (ya creado en 4.3)
CREATE INDEX idx_places_location ON places USING GIST(location);

-- Índice parcial para lugares activos
CREATE INDEX idx_places_active ON places(is_active) WHERE is_active = true;
```

#### Plan de Ejecución Esperado

```
Limit  (cost=100.00..150.00 rows=20 width=500)
  ->  Sort  (cost=100.00..150.00 rows=100 width=500)
        Sort Key: (st_distance(...))
        ->  Nested Loop  (cost=0.50..90.00 rows=100 width=500)
              ->  Index Scan using idx_places_active on places p
                    Filter: (location IS NOT NULL AND st_dwithin(...))
              ->  Index Scan using categories_pkey on categories c
                    Index Cond: (id = p.category_id)
```

### 2.2 Búsqueda por Texto — CRÍTICA

**Problema:** Búsqueda fuzzy con soporte para acentos y typos.

#### Consulta Optimizada

```sql
-- ✅ Búsqueda full-text con trigram + unaccent
SELECT 
    p.id,
    p.name,
    p.description,
    p.address,
    p.rating_avg,
    c.name as category_name,
    similarity(unaccent(p.name), unaccent($1)) as match_score
FROM places p
JOIN categories c ON p.category_id = c.id
WHERE p.is_active = true
AND (
    unaccent(p.name) % unaccent($1)  -- trigram similarity
    OR unaccent(p.description) % unaccent($1)
    OR p.name ILIKE '%' || $1 || '%'  -- fallback exacto
)
ORDER BY match_score DESC, p.rating_avg DESC
LIMIT 20;
```

**Tiempo estimado:** ~30ms

**Optimizaciones aplicadas:**
1. **Índice GIN con trigram:** `CREATE INDEX idx_places_name_trgm ON places USING GIN(name gin_trgm_ops);`
2. **Extensión unaccent:** Permite buscar "catedral" y encontrar "Catedral"
3. **Threshold de similitud:** Configurar `pg_trgm.similarity_threshold = 0.3`

#### Índices Requeridos

```sql
-- Índice GIN para búsqueda fuzzy por nombre
CREATE INDEX idx_places_name_trgm ON places USING GIN(name gin_trgm_ops);

-- Índice GIN para búsqueda en descripción (opcional, más peso en nombre)
CREATE INDEX idx_places_desc_trgm ON places USING GIN(description gin_trgm_ops);
```

### 2.3 Listado por Categoría — ALTA

#### Consulta Optimizada

```sql
-- ✅ Listado paginado por categoría con cursor
SELECT 
    p.id,
    p.name,
    p.description,
    p.address,
    p.rating_avg,
    p.rating_count,
    (
        SELECT url FROM place_photos pp
        WHERE pp.place_id = p.id 
        ORDER BY pp.display_order 
        LIMIT 1
    ) as primary_photo
FROM places p
WHERE p.category_id = $1
AND p.is_active = true
AND p.id > $2  -- cursor pagination (más eficiente que OFFSET)
ORDER BY p.rating_avg DESC, p.id ASC
LIMIT 20;
```

**Tiempo estimado:** ~5ms

**Optimizaciones:**
1. **Cursor pagination:** `WHERE id > last_seen_id` en lugar de `OFFSET`
2. **Índice compuesto:** `CREATE INDEX idx_places_category_rating ON places(category_id, rating_avg DESC) WHERE is_active = true;`

### 2.4 Detalle de Lugar — ALTA

#### Consulta Optimizada

```sql
-- ✅ Detalle completo con N+1 queries eliminado
SELECT 
    p.*,
    c.name as category_name,
    c.icon as category_icon,
    u.name as owner_name,
    (
        SELECT json_agg(json_build_object(
            'id', pp.id,
            'url', pp.url,
            'alt_text', pp.alt_text,
            'display_order', pp.display_order
        ) ORDER BY pp.display_order)
        FROM place_photos pp
        WHERE pp.place_id = p.id
    ) as photos,
    (
        SELECT json_agg(json_build_object(
            'day_of_week', ph.day_of_week,
            'open_time', ph.open_time,
            'close_time', ph.close_time,
            'is_closed', ph.is_closed
        ) ORDER BY ph.day_of_week)
        FROM place_hours ph
        WHERE ph.place_id = p.id
    ) as hours
FROM places p
JOIN categories c ON p.category_id = c.id
LEFT JOIN users u ON p.owner_id = u.id
WHERE p.id = $1
AND p.is_active = true;
```

**Tiempo estimado:** ~3ms

**Optimizaciones:**
1. **JSON aggregation:** Evita N+1 queries para fotos y horarios
2. **Subqueries correlacionadas:** Solo ejecutan si hay datos

### 2.5 Clustering de Mapa — ALTA

#### Consulta Optimizada

```sql
-- ✅ Clustering usando ST_ClusterDBSCAN con bounding box
WITH bounded_places AS (
    SELECT id, location, latitude, longitude
    FROM places
    WHERE is_active = true
    AND latitude BETWEEN $4 AND $1    -- southWestLat, northEastLat
    AND longitude BETWEEN $2 AND $3  -- southWestLng, northEastLng
),
clustered AS (
    SELECT 
        id,
        latitude,
        longitude,
        ST_ClusterDBSCAN(location, eps := $5, minpoints := 2) OVER () as cluster_id
    FROM bounded_places
)
SELECT 
    COALESCE(cluster_id, -1) as cluster_id,
    COUNT(*) as cluster_count,
    AVG(latitude)::DECIMAL(10,8) as avg_lat,
    AVG(longitude)::DECIMAL(11,8) as avg_lng,
    array_agg(id) as place_ids
FROM clustered
GROUP BY cluster_id
ORDER BY cluster_count DESC;
```

**Tiempo estimado (1,000 lugares):** ~50ms

**Optimizaciones:**
1. **Bounding box pre-filter:** Reduce lugares antes del clustering
2. **Índice en lat/lng:** `CREATE INDEX idx_places_lat_lng ON places(latitude, longitude) WHERE is_active = true;`

### 2.6 Reseñas de Lugar — MEDIA

#### Consulta Optimizada

```sql
-- ✅ Reseñas aprobadas con usuario y respuestas
SELECT 
    r.id,
    r.rating,
    r.comment,
    r.photos,
    r.visit_date,
    r.created_at,
    json_build_object(
        'id', u.id,
        'name', u.name,
        'photo_url', u.photo_url
    ) as user,
    (
        SELECT json_agg(json_build_object(
            'id', rr.id,
            'comment', rr.comment,
            'created_at', rr.created_at,
            'user_name', ru.name
        ) ORDER BY rr.created_at)
        FROM review_replies rr
        JOIN users ru ON rr.user_id = ru.id
        WHERE rr.review_id = r.id
    ) as replies
FROM reviews r
JOIN users u ON r.user_id = u.id
WHERE r.place_id = $1
AND r.is_approved = true
ORDER BY r.created_at DESC
LIMIT $2 OFFSET $3;
```

**Tiempo estimado:** ~10ms

### 2.8 Eventos Activos — MEDIA

```sql
-- ✅ Eventos con filtro de fecha y orden cronológico
SELECT 
    e.*,
    CASE 
        WHEN e.date_start > NOW() THEN 'upcoming'
        WHEN e.date_end IS NOT NULL AND e.date_end < NOW() THEN 'past'
        ELSE 'ongoing'
    END as event_status
FROM events e
WHERE e.is_active = true
AND (e.date_end IS NULL OR e.date_end >= NOW())
ORDER BY e.date_start ASC
LIMIT 20;
```

**Índice:**
```sql
CREATE INDEX idx_events_active_dates ON events(date_start, date_end) WHERE is_active = true;
```

### 3.2 Extensiones de Monitoreo

```sql
-- pg_stat_statements para análisis de queries
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Top 10 queries más lentas
SELECT 
    query,
    calls,
    total_exec_time / calls as avg_time_ms,
    rows / calls as avg_rows
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

## 5. Monitoreo de Performance

### 5.1 Métricas Clave

| Métrica | Target | Alerta |
|---------|--------|--------|
| Query time (p95) | < 50ms | > 200ms |
| Connections activas | < 80% pool | > 90% |
| Cache hit ratio | > 95% | < 90% |
| Dead tuples | < 5% | > 10% |
| Index usage | > 99% | < 95% |

### 5.2 Queries de Monitoreo

```sql
-- Cache hit ratio
SELECT 
    sum(heap_blks_hit) / (sum(heap_blks_hit) + sum(heap_blks_read)) as cache_hit_ratio
FROM pg_statio_user_tables;

-- Uso de índices
SELECT 
    schemaname,
    tablename,
    indexname,
    idx_scan as index_scans,
    idx_tup_read as tuples_read,
    idx_tup_fetch as tuples_fetched
FROM pg_stat_user_indexes
WHERE schemaname = 'public'
ORDER BY idx_scan DESC;

-- Tablas con más dead tuples
SELECT 
    schemaname,
    tablename,
    n_dead_tup,
    n_live_tup,
    round(n_dead_tup::numeric / GREATEST(n_live_tup, 1) * 100, 2) as dead_ratio
FROM pg_stat_user_tables
WHERE schemaname = 'public'
ORDER BY n_dead_tup DESC;
```
