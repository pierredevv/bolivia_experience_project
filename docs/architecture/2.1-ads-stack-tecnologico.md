## ADR-201: Framework Móvil — Flutter

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
Se necesita un framework multiplataforma para desarrollo móvil que cubra Android (80% mercado Bolivia) e iOS (20%) con un solo codebase. Restricciones: dispositivos gama media-baja (2-4 GB RAM), conectividad variable, presupuesto limitado.

**Opciones consideradas:**
- Opción A — Flutter 3.x
  · Ventajas: Multiplataforma nativo, rendimiento cercano a nativo, Hot Reload, comunidad activa, soporte Google, widgets Material Design 3, buen manejo de estado
  · Desventajas: Tamaño del bundle mayor que React Native, ecosistema de paquetes menor que nativo
- Opción B — React Native
  · Ventajas: JavaScript conocido, ecosistema NPM mayor, CodePush para updates
  · Desventajas: Rendimiento inferior en animaciones complejas, puente JS overhead, dependencia de comunidades para nativo modules
- Opción C — Kotlin Multiplatform (KMP)
  · Ventajas: Lógica compartida nativa, acceso directo a APIs nativas
  · Desventajas: UI debe escribirse por separado (no es truly cross-platform), madurez limitada, comunidad pequeña
- Opción D — Desarrollo nativo separado (Kotlin/Swift)
  · Ventajas: Máximo rendimiento, acceso completo a APIs
  · Desventajas: Dos codebases, duplicación de esfuerzo, costo duplicado, presupuesto insuficiente

**Decisión:**
Flutter 3.x con Dart 3 como framework móvil principal.

**Justificación:**
1. **Un solo codebase** para Android e iOS reduce costo y tiempo de desarrollo en ~40%
2. **Rendimiento nativo** compila a ARM nativo, sin puente JavaScript
3. **Material Design 3** nativo para UI consistente con el design system
4. **Hot Reload** acelera desarrollo iterativo
5. **Gestión de estado** con Riverpod (definido en ADR-219)
6. **Comunidad creciente** en Latinoamérica, soporte de Google
7. **Optimización para dispositivos bajos** permite control fino del rendimiento

**Consecuencias:**
- Positivas: Desarrollo rápido, UI consistente, rendimiento aceptable
- Negativas: Tamaño de app (~15-20MB), paquetes nativos pueden requerir platform channels
- Deuda técnica: Posible migración a KMP si Flutter pierde soporte (riesgo bajo)

**Revisión:** Revisar después de 12 meses. EvaluarFlutter 4.x y evolución del ecosistema.

## ADR-202: Framework Web — React + Vite + TypeScript

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
Se necesitan dos paneles web: Administrativo (BackOffice) y de Empresas. Requieren: autenticación, RBAC, CRUD, dashboards, responsive design. Equipo tiene experiencia en React.

**Opciones consideradas:**
- Opción A — React 18 + Vite + TypeScript
  · Ventajas: Ecosistema maduro, TypeScript para type safety, Vite para build rápido, HMR instantáneo, gran comunidad
  · Desventajas: Configuración inicial más compleja que alternativas opinionadas
- Opción B — Next.js
  · Ventajas: SSR/SSG, routing basado en archivos, optimizaciones integradas
  · Desventajas: Overkill para dashboards internos, complejidad innecesaria, server-side no requerido
- Opción C — Angular
  · Ventajas: Opinionado, completo, RxJS para async
  · Desventajas: Curva de aprendizaje alta, bundle mayor, menos popular en startups
- Opción D — Vue 3 + Vite
  · Ventajas: Simple, reactividad intuitiva, curva de aprendizaje baja
  · Desventajas: Menor ecosistema empresarial, menos TypeScript-first que React

**Decisión:**
React 18 + Vite + TypeScript para ambos paneles web.

**Justificación:**
1. **TypeScript** previene errores en tiempo de compilación, mejora mantenibilidad
2. **Vite** ofrece HMR instantáneo y build optimizado (~10x más rápido que Webpack)
3. **React 18** soporta Concurrent Features para UI Responsiva
4. **Ecosistema maduro**: component libraries (Ant Design, MUI), formularios (React Hook Form)
5. **Reutilización**: componentes compartidos entre admin y panel empresa
6. **Equipo con experiencia** en React reduce curva de aprendizaje

**Consecuencias:**
- Positivas: Desarrollo rápido, type safety, hot reload, comunidad activa
- Negativas: Configuración inicial manual (no opinionado como Next.js)
- Deuda técnica: Ninguna significativa

**Revisión:** Revisar después de 12 meses. Evaluar React Server Components si se requieren dashboards públicos.

## ADR-203: Framework Backend — NestJS

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
Se necesita un backend API RESTful que sirva a la app móvil y los paneles web. Requiere: autenticación JWT, RBAC, validación, documentación automática, arquitectura modular, soporte TypeScript.

**Opciones consideradas:**
- Opción A — NestJS 10
  · Ventajas: Arquitectura hexagonal nativa, TypeScript first, inyección de dependencias, decoradores, guards, interceptors, microservicios-ready, Swagger integrado
  · Desventajas: Curva de aprendizaje para patrones (guards, pipes), más verboso que Express
- Opción B — Express.js + TypeScript
  · Ventajas: Simple, flexible, enorme comunidad, muchos middleware disponibles
  · Desventajas: No opinionado, sin arquitectura definida, cada proyecto es diferente, más propenso a deuda técnica
- Opción C — Fastify + TypeScript
  · Ventajas: Más rápido que Express, schema-based validation, plugin system
  · Desventajas: Menor comunidad que Express, menos middleware disponible
- Opción D — AdonisJS
  · Ventajas: Opinionado, completo, Laravel-like para Node.js
  · Desventajas: Menor comunidad que NestJS, menos flexibilidad

**Decisión:**
NestJS 10 como framework backend principal.

**Justificación:**
1. **Arquitectura hexagonal** forzada por el framework (Domain, Application, Infrastructure, Presentation)
2. **TypeScript first** con decoradores para metadatos
3. **Inyección de dependencias** nativa para testing y desacoplamiento
4. **Guards** para autorización (RBAC), **Interceptors** para logging, **Pipes** para validación
5. **Swagger/OpenAPI** integrado con decoradores
6. **Microservicios-ready** para escalabilidad futura
7. **Comunidad activa** y bien documentada

**Consecuencias:**
- Positivas: Arquitectura consistente, testable, documentación automática
- Negativas: Más verboso que Express, curva de aprendizaje para patrones avanzados
- Deuda técnica: Ninguna significativa

**Revisión:** Revisar después de 12 meses. Evaluar NestJS 11 y nuevas features.

## ADR-204: Base de Datos — PostgreSQL + PostGIS

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
Se necesita una base de datos relacional robusta que soporte: consultas geoespaciales (búsqueda por distancia, puntos dentro de radio),全文搜索, JSON, transacciones ACID, escalabilidad vertical.

**Opciones consideradas:**
- Opción A — PostgreSQL 15 + PostGIS
  · Ventajas: Soporte geoespacial nativo (PostGIS), ACID, JSONB,全文搜索, extensions, madurez, rendimiento comprobado
  · Desventajas: Complejidad de PostGIS, curva de aprendizaje para consultas geoespaciales
- Opción B — MongoDB + GeoJSON
  · Ventajas: Flexibilidad de esquema, geo queries con $geoNear, documentos anidados
  · Desventajas: No ACID completo, consistencia eventual, joins limitados, menos madurez para analytics
- Opción C — MySQL 8 + Spatial Extensions
  · Ventajas: Popular, hosting barato, MySQL Workbench
  · Desventajas: Soporte geoespacial limitado vs PostGIS, menos extensions, menos features avanzadas
- Opción D — Firebase Firestore
  · Ventajas: Serverless, sync en tiempo real, sin gestión de infraestructura
  · Desventajas: Vendor lock-in, queries limitadas, costos impredecibles a escala, sin geoespacial nativo

**Decisión:**
PostgreSQL 15 con extensión PostGIS para base de datos principal.

**Justificación:**
1. **PostGIS** es el estándar de oro para consultas geoespaciales en bases de datos
2. **ACID completo** garantiza consistencia para transacciones
3. **JSONB** permite almacenar datos semi-estructurados (horarios, metadata)
4. **全文搜索** nativa elimina necesidad de Elasticsearch para MVP
5. **Extensions** (PostGIS, pg_trgm, pgcrypto) extienden funcionalidad
6. **Madurez** y estabilidad comprobada en producción
7. **Costo**: Hosting en Cloud SQL es razonable para MVP

**Consecuencias:**
- Positivas: Consultas geoespaciales potentes, consistencia, escalabilidad
- Negativas: Requiere aprendizaje de PostGIS, gestión de índices espaciales
- Deuda técnica: Ninguna significativa

**Revisión:** Revisar después de 12 meses. Evaluar PostgreSQL 17 y nuevas extensions.

## ADR-205: ORM — Prisma

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
Se necesita un ORM para Node.js/NestJS que proporcione: type safety, migraciones, schema management, query builder, soporte PostgreSQL + PostGIS.

**Opciones consideradas:**
- Opción A — Prisma 5.x
  · Ventajas: Type safety completo, migraciones declarativas, Prisma Client generado, schema.prisma como source of truth, buen DX
  · Desventajas: Soporte limitado para PostGIS (raw queries necesarias), generador de código, menos flexible que query builders
- Opción B — TypeORM
  · Ventajas: Decorators (similar a Hibernate), entity-first, migraciones, soporte PostgreSQL
  · Desventajas: Menos type safety que Prisma, bugs conocidos, comunidad en declive
- Opción C — Knex.js (query builder, no ORM)
  · Ventajas: Flexible,SQL-like, sin magia, buen soporte PostGIS
  · Desventajas: No es ORM (sin entities), sin type safety automático, más código manual
- Opción D — Drizzle ORM
  · Ventajas: TypeScript first, SQL-like, performante, soporte PostGIS
  · Desventajas: Más nuevo, menor comunidad, menos docs

**Decisión:**
Prisma 5.x como ORM principal, con raw queries para consultas geoespaciales complejas.

**Justificación:**
1. **Type safety** completo: Prisma Client genera tipos automáticamente desde schema.prisma
2. **Migraciones** declarativas y reversibles
3. **Schema como source of truth**: schema.prisma documenta el modelo de datos
4. **DX excelente**: autocompletado, error detection en tiempo de compilación
5. **Integración NestJS** oficial (@nestjs/prisma)
6. **Comunidad activa** y bien mantenida

**Limitación conocida:**
- Prisma tiene soporte limitado para PostGIS. Las consultas geoespaciales complejas se implementarán con raw queries de Prisma (`$queryRaw` y `$executeRaw`).

**Consecuencias:**
- Positivas: Type safety, migraciones, DX, documentación automática
- Negativas: PostGIS requiere raw queries, menos flexible que Knex para queries complejas
- Deuda técnica: Posible migración a Drizzle si Prisma no mejora soporte PostGIS

**Revisión:** Revisar después de 12 meses. Evaluar Drizzle ORM y soporte PostGIS en Prisma.

## ADR-206: Autenticación — Firebase Auth + JWT

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
Se necesita un sistema de autenticación que soporte: email/password, Google OAuth, JWT para APIs, refresh tokens, RBAC (Admin, Empresa, Usuario).

**Opciones consideradas:**
- Opción A — Firebase Authentication + JWT personalizado
  · Ventajas: Google maneja auth (infraestructura), JWT para APIs, Google OAuth nativo, multi-tenant ready
  · Desventajas: Vendor lock-in parcial, latencia adicional, dependencia de Firebase
- Opción B — Auth0
  · Ventajas: Completo, multi-protocolo, MFA, social logins
  · Desventajas: Costo alto para startups, vendor lock-in, overkill para MVP
- Opción C — AWS Cognito
  · Ventajas: Integración AWS, user pools, hosted UI
  · Desventajas: Complejo, UX mediocre, pricing confuso
- Opción D — Passport.js personalizado
  · Ventajas: Flexible, sin vendor lock-in, control total
  · Desventajas: Requiere infraestructura propia, más código, OAuth manual

**Decisión:**
Firebase Authentication como proveedor de identidad, con generación de JWT personalizados en el backend.

**Flujo de autenticación:**
```
1. Usuario se autentica con Firebase Auth (email/password o Google)
2. Firebase retorna Firebase ID Token
3. Backend valida el token con Firebase Admin SDK
4. Backend genera JWT personalizado (access + refresh tokens)
5. App usa JWT personalizado para todas las llamadas API
```

**Justificación:**
1. **Google maneja la infraestructura** de autenticación (disponibilidad, seguridad)
2. **Google OAuth nativo** sin configuración adicional
3. **JWT personalizado** permite control total sobre claims, expiración, RBAC
4. **Refresh tokens** para sesiones persistentes (7 días)
5. **Firebase Admin SDK** valida tokens server-side de forma segura
6. **Multi-tenant ready** para soportar roles (Admin, Empresa, Usuario)

**Consecuencias:**
- Positivas: Autenticación robusta, OAuth simplificado, JWT controlable
- Negativas: Vendor lock-in parcial con Firebase, latencia de validación
- Deuda técnica: Posible migración a Auth0 si Firebase no escala

**Revisión:** Revisar después de 12 meses. Evaluar costo de Firebase y alternativas.

## ADR-207: OAuth — Google OAuth 2.0

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
Los usuarios deben poder iniciar sesión con su cuenta de Google de forma rápida y segura.

**Opciones consideradas:**
- Opción A — Google OAuth 2.0 (via Firebase Auth)
  · Ventajas: Nativo en Firebase, un tap para iniciar sesión, sin contraseña que recordar
  · Desventajas: Dependencia de Google, requiere configuración de OAuth consent screen
- Opción B — Facebook Login
  · Ventajas: Popular en Bolivia, integración con Instagram
  · Desventajas: Percepción negativa de privacidad, menos usado para auth
- Opción C — Apple Sign In
  · Ventajas: Requerido por App Store para apps con otros social logins
  · Desventajas: Menos usuarios en Bolivia, configuración más compleja
- Opción D — Solo email/password
  · Ventajas: Simple, sin dependencias
  · Desventajas: Fricción alta, usuarios olvidan contraseñas

**Decisión:**
Google OAuth 2.0 como único social login en MVP.

**Justificación:**
1. **Google domina en Bolivia** (~95% uso de búsqueda, Gmail popular)
2. **Un tap para iniciar sesión** reduce fricción de registro
3. **Firebase Auth** integra Google OAuth nativamente
4. **Seguridad**: Google maneja contraseñas y 2FA
5. **Apple Sign In** se agregará en Fase 2 si se requiere para App Store

**Consecuencias:**
- Positivas: Registro rápido, menor abandono, sin contraseñas
- Negativas: Dependencia de Google, usuario sin Google no puede usar social login
- Deuda técnica: Agregar Apple Sign In en Fase 2

**Revisión:** Revisar después de 3 meses. Evaluar métricas de registro con Google vs email.

## ADR-208: Almacenamiento de Archivos — Firebase Storage

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
Se necesita almacenar: fotos de lugares (galería), fotos de perfil de usuario, fotos de opiniones, assets de la app.

**Opciones consideradas:**
- Opción A — Firebase Storage (Cloud Storage for Firebase)
  · Ventajas: Integración nativa con Firebase Auth, CDN automático, escalable, reglas de seguridad
  · Desventajas: Vendor lock-in, costos pueden escalar rápido, menos control que GCS directo
- Opción B — Google Cloud Storage (GCS) directo
  · Ventajas: Más control, reglas personalizadas, integración con GCP
  · Desventajas: Más configuración, sin CDN automático (requiere Cloud CDN)
- Opción C — AWS S3
  · Ventajas: Estándar de la industria, inexpensive, CDN con CloudFront
  · Desventajas: Vendor lock-in AWS, más configuración, no integrado con Firebase
- Opción D — Cloudinary
  · Ventajas: Optimización automática de imágenes, transforms, CDN
  · Desventajas: Costo alto a escala, vendor lock-in, overkill para MVP

**Decisión:**
Firebase Storage para almacenamiento de archivos.

**Justificación:**
1. **Integración nativa** con Firebase Auth (reglas de seguridad por usuario)
2. **CDN automático** para servir imágenes rápidamente
3. **Escalabilidad** automática sin gestión
4. **Reglas de seguridad** basadas en autenticación
5. **Costos predecibles** para MVP (~$5-25/mes)

**Consecuencias:**
- Positivas: Integración simple, CDN, escalabilidad
- Negativas: Vendor lock-in, costos a escala
- Deuda técnica: Posible migración a GCS si se requiere más control

**Revisión:** Revisar después de 6 meses. Evaluar costos y necesidades de almacenamiento.

## ADR-209: Mapas Móvil — Google Maps Flutter SDK

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
La app requiere un mapa interactivo con: marcadores, clustering, ubicación actual, búsqueda de lugares.

**Opciones consideradas:**
- Opción A — Google Maps Flutter SDK
  · Ventajas: Oficial de Google, clustering incluido, ubicación precisa, Street View, directions
  · Desventajas: Requiere API key, costos por uso, dependencia de Google
- Opción B — Mapbox
  · Ventajas: Personalización avanzada, offline maps, estilo custom
  · Desventajas: Costo mayor, configuración más compleja, menos popular en LATAM
- Opción C — Leafmap (open source)
  · Ventajas: Gratis, sin vendor lock-in, personalizable
  · Desventajas: Requiere más trabajo, sin soporte oficial, clustering manual
- Opción D — flutter_map + OpenStreetMap
  · Ventajas: Gratis, open source, sin API key
  · Desventajas: Sin clustering nativo, ubicación menos precisa, más código

Google Maps Flutter SDK como mapa principal.

**Justificación:**
1. **Los usuarios ya conocen Google Maps** en Bolivia (~70% uso)
2. **Clustering incluido** para manejar múltiples marcadores
3. **Ubicación precisa** con GPS
4. **Directions API** para "Cómo llegar"
5. **Street View** para vista previa de lugares
6. **Costos bajos** para uso moderado (free tier: $200/mes)

**Consecuencias:**
- Positivas: Experiencia familiar para usuarios, funcionalidades completas
- Negativas: Requiere API key, costos a escala, dependencia de Google
- Deuda técnica: Posible add-on con Mapbox para offline maps

**Revisión:** Revisar después de 6 meses. Evaluar costos de API y alternativas offline.

## ADR-211: Navegación Externa — Google Maps + Waze Deep Links

// Deep links
const googleMapsUrl = 'https://www.google.com/maps/dir/?api=1&destination=$lat,$lng';

**Justificación:**
1. **Google Maps** es el navegador #1 en Bolivia
2. **Waze** es popular entre conductores (propiedad de Google)
3. **Deep links** son simples de implementar
4. **Sin dependencia** de SDK nativo (abre app externa)

**Consecuencias:**
- Positivas: Experiencia familiar, sin código nativo complejo
- Negativas: Usuario debe tener la app instalada
- Deuda técnica: Agregar Apple Maps para iOS en Fase 2

**Revisión:** Revisar después de 3 meses. Evaluar uso de cada navegador.

## ADR-213: Contenedores — Docker + Docker Compose

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
Se necesita consistencia entre ambientes de desarrollo, testing y producción.

**Opciones consideradas:**
- Opción A — Docker + Docker Compose
  · Ventajas: Estándar de la industria, multi-stage builds, compose para orquestación local
  · Desventajas: Curva de aprendizaje, overhead en desarrollo local
- Opción B — Podman + Podman Compose
  · Ventajas: Daemonless, rootless, más seguro
  · Desventajas: Menor compatibilidad con Docker Hub, menos docs
- Opción C — Nix
  · Ventajas: Reproducibilidad total, immutable
  · Desventajas: Curva de aprendizaje muy alta, comunidad pequeña

**Decisión:**
Docker 24 + Docker Compose v2 para contenedores.

**Justificación:**
1. **Estándar de la industria**: todos los desarrolladores lo conocen
2. **Multi-stage builds**: imágenes optimizadas para producción
3. **Docker Compose**: orquestación simple para desarrollo local
4. **GitHub Actions** soporta Docker nativamente
5. **GCP Cloud Run** soporta Dockerfiles

**Consecuencias:**

## ADR-217: Control de Versiones — GitHub + Git Flow

**Contexto:**
Se necesita un flujo de trabajo para gestión de código que soporte: múltiples desarrolladores, releases, hotfixes, features paralelas.

**Opciones consideradas:**
- Opción A — GitHub + Git Flow
  · Ventajas: Flujo estructurado, branches para features/release/hotfix, ideal para releases programados
  · Desventajas: Más branches que GitHub Flow, complejidad para equipos pequeños
- Opción B — GitHub + GitHub Flow
  · Ventajas: Simple, solo main + feature branches, ideal para deployment continuo
  · Desventajas: Sin branches de release, menos estructurado para releases versionadas
- Opción C — GitHub + Trunk-Based Development
  · Ventajas: Simple, feature flags, ideal para deployment continuo
  · Desventajas: Requiere feature flags, testing más complejo, no ideal para releases

**Decisión:**
GitHub + Git Flow para control de versiones.

**Estructura de branches:**
```
main          ← Producción (releases versionados)
  ↑
develop       ← Desarrollo integrado
  ↑
feature/*     ← Features individuales
release/*     ← Preparación de release
hotfix/*      ← Fixes urgentes
```

**Justificación:**
1. **Git Flow** es ideal para releases versionados (Semantic Versioning)
2. **Branches de release** permiten testing antes de producción
3. **Hotfixes** se aplican rápidamente sin afectar develop
4. **GitHub** soporta Git Flow nativamente con保护 de branches

**Consecuencias:**
- Positivas: Flujo estructurado, releases controlados, hotfixes rápidos
- Negativas: Más branches que GitHub Flow, overhead para cambios simples
- Deuda técnica: Posible migración a GitHub Flow si el equipo crece

**Revisión:** Revisar después de 6 meses. Evaluar si Git Flow es demasiado complejo.

## ADR-219: Gestión de Estado Flutter — Riverpod

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
La app Flutter requiere una solución de gestión de estado que sea: type-safe, testable, escalable, sin boilerplate excesivo.

**Opciones consideradas:**
- Opción A — Riverpod
  · Ventajas: Type-safe, compilación null-safe, providers declarativos, testing fácil, sin BuildContext

  · Ventajas: Simple, menos boilerplate, routing integrado

- Positivas: Type safety, testing, escalabilidad, menos boilerplate que BLoC
- Negativas: Curva de aprendizaje para devs acostumbrados a BLoC
- Deuda técnica: Ninguna significativa

## ADR-220: Consultas Geoespaciales — Prisma Raw Queries + PostGIS

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
La funcionalidad core de la app requiere consultas geoespaciales: búsqueda por distancia, puntos dentro de un radio, clustering.

**Problema:**
Prisma tiene soporte limitado para extensiones PostGIS. No existe soporte nativo para tipos `geography`, `geometry`, ni funciones espaciales (`ST_Distance`, `ST_DWithin`, `ST_Cluster`).

**Opciones consideradas:**
- Opción A — Prisma raw queries ($queryRaw) + PostGIS
  · Ventajas: Aprovecha Prisma para CRUD normal, raw queries para geoespacial, sin otro ORM
  · Desventajas: Raw queries no type-safe, SQL dinámico, más propenso a errores
- Opción B — Knex.js como query builder complementario
  · Ventajas: Type-safe queries geoespaciales, SQL builder elegante
  · Desventajas: Dos ORM/query builders en el mismo proyecto, complejidad
- Opción C — Vistas materializadas
  · Ventajas: Pre-calculadas, rápidas para lecturas
  · Desventajas: Requieren refresh, no actualizadas en tiempo real
- Opción D — Stored procedures
  · Ventajas: Lógica en la DB, performante
  · Desventajas: Difícil de mantener, testing complejo, vendor lock-in

**Decisión:**
Opción A — Prisma raw queries ($queryRaw) + PostGIS.

**Implementación:**
```typescript
// Ejemplo: Buscar lugares dentro de un radio de 5km
const places = await prisma.$queryRaw`
  SELECT id, name, category, 
    ST_Distance(
      location::geography,
      ST_SetSRID(ST_MakePoint(${lng}, ${lat}), 4326)::geography
    ) as distance_meters
  FROM places
  WHERE ST_DWithin(
    location::geography,
    ST_SetSRID(ST_MakePoint(${lng}, ${lat}), 4326)::geography,
    ${radiusMeters}
  )
  ORDER BY distance_meters ASC
  LIMIT ${limit}
`;
```

**Justificación:**
1. **Reutiliza Prisma** para CRUD normal (95% de las queries)
2. **Raw queries** solo para consultas geoespaciales (5% de las queries)
3. **Sin dependencia adicional** (no Knex, no otro ORM)
4. **PostGIS** es el estándar para consultas espaciales
5. **Performance**: queries geoespaciales optimizadas con índices GIST

**Consecuencias:**
- Positivas: Solución simple, sin dependencias adicionales, performante
- Negativas: Raw queries no type-safe, SQL dinámico
- Deuda técnica: Posible migración a Drizzle ORM si Prisma no mejora

**Revisión:** Revisar después de 12 meses. Evaluar Drizzle ORM y soporte PostGIS en Prisma.
