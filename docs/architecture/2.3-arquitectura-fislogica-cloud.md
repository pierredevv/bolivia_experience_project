### Principios de Arquitectura Lógica

| Principio | Implementación |
|-----------|---------------|
| **Separación de Capas** | Cada capa solo depende de la capa inmediatamente inferior |
| **Dependencia hacia Adentro** | Domain no depende de Infrastructure |
| **Inversión de Dependencias** | Domain define interfaces, Infrastructure las implementa |
| **单一 Responsabilidad** | Cada módulo tiene una responsabilidad clara |
| **Open/Closed** | Abierto a extensión, cerrado a modificación |

### docker-compose.yml

```yaml
version: '3.8'

services:
  nginx:
    image: nginx:alpine
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/conf.d:/etc/nginx/conf.d
      - ./nginx/ssl:/etc/nginx/ssl
    depends_on:
      - api-backend
    networks:
      - bolivia-experience

  api-backend:
    build:
      context: ./api
      dockerfile: Dockerfile
    ports:
      - "3000:3000"
    environment:
      - DATABASE_URL=postgresql://postgres:postgres@postgres:5432/bolivia_experience
      - FIREBASE_PROJECT_ID=${FIREBASE_PROJECT_ID}
      - FIREBASE_PRIVATE_KEY=${FIREBASE_PRIVATE_KEY}
      - FIREBASE_CLIENT_EMAIL=${FIREBASE_CLIENT_EMAIL}
      - GOOGLE_MAPS_API_KEY=${GOOGLE_MAPS_API_KEY}
      - OPENWEATHER_API_KEY=${OPENWEATHER_API_KEY}
      - JWT_SECRET=${JWT_SECRET}
      - JWT_EXPIRATION=15m
      - REFRESH_TOKEN_EXPIRATION=7d
    depends_on:
      - postgres
    networks:
      - bolivia-experience

  postgres:
    image: postgis/postgis:15-3.3-alpine
    ports:
      - "5432:5432"
    environment:
      - POSTGRES_DB=bolivia_experience
      - POSTGRES_USER=postgres
      - POSTGRES_PASSWORD=postgres
    volumes:
      - postgres_data:/var/lib/postgresql/data
    networks:
      - bolivia-experience

  redis:
    image: redis:7-alpine
    ports:
      - "6379:6379"
    networks:
      - bolivia-experience

volumes:
  postgres_data:

networks:
  bolivia-experience:
    driver: bridge
```

## ADR-221: Arquitectura Cloud en GCP

**Fecha:** 2026-06-26
**Estado:** Aceptado

**Contexto:**
Definir la arquitectura de infraestructura en la nube para el entorno de producción.

**Opciones consideradas:**
- Opción A — Cloud Run (Serverless)
  · Ventajas: Auto-scaling, pay-per-use, sin gestión de servidores
  · Desventajas: Cold starts, limitaciones de ejecución
- Opción B — Compute Engine (VMs)
  · Ventajas: Control total, sin limitaciones de ejecución
  · Desventajas: Requiere gestión de OS, patches, escalabilidad manual
- Opción C — Kubernetes Engine (GKE)
  · Ventajas: Orquestación completa, escalabilidad avanzada
  · Desventajas: Complejidad alta, overkill para MVP

**Decisión:**
Cloud Run para API y paneles web, Cloud SQL para base de datos.

**Justificación:**
1. **Pay-per-use**: escala a cero cuando no hay tráfico
2. **Auto-scaling**: maneja picos de tráfico automáticamente
3. **Sin gestión de servidores**: menor carga operativa
4. **Integración con GCP**: Firebase, Cloud SQL, Secret Manager
5. **Costo bajo para MVP**: ~$85-231/mes

**Consecuencias:**
- Positivas: Menor carga operativa, escalabilidad automática
- Negativas: Cold starts (mejorable con min instances), vendor lock-in
- Deuda técnica: Posible migración a GKE si se requiere más control
